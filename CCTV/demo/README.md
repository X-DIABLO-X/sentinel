# Physics-render demo clips

Generated by `scripts/render_physics_demo.py`: NETRA's own detector + tracker
(`netra/detect.py`, `netra/track.py`) feeding live `Track` objects directly into
our rotation-gate physics engine (`netra/events/rotation_gate.py`,
`score_pairs()`), with the result drawn back onto the video as a HUD overlay
— per-vehicle speed (px/s + labelled km/h estimate), acceleration, momentum,
trajectory trail, and — where the engine found a candidate — the pair boxed
red with score, interaction type, and a `<< CONTACT` marker at the
sub-frame-refined contact instant.

Live in the operator console at `/cctv` — **"Physics demo — rotation-gate
engine"** (`GET /api/demo-videos`) lists every `*_physics_result.json`
actually present in this folder, so the panel never drifts out of sync with
what's really on disk.

These are **NETRA's own test clips** (`data/problems/{Accidents,Traffic}/`),
run through the merged pipeline for the first time in this exact combined
form — a genuine first-look test, not a re-run of something already tuned to
these specific clips. `4/11/13/14` were re-rendered with the acceleration/
momentum HUD added — detection and scoring are deterministic, so their
pair/score/interaction numbers below are unchanged from the first run;
`7/8/9/12` are new.

## Read this before using these in the demo video

**The Traffic clip's 0.738 score has been manually reviewed and is very
likely a false positive, not a real event — this is now a confirmed finding,
not an open question.** Frame inspection at its reported contact instant
(t≈1.13s) shows dense, queued intersection traffic, not a collision. The
tracker produced **227 distinct track IDs over only 221 frames** — severe
identity-switch churn — and one of the two "colliding" tracks was assigned
an instantaneous speed of **1915 px/s** (crossing the full frame width in
about a second) while visually stationary in the queue. This is the
rotation-gate reading tracker noise as a T-bone. It is *exactly* the
queue-vs-collision confusion the module's own docstring warns about, and
exactly why NETRA's wired `netra/events/collision.py` requires
`fixed_camera_min_channels: 2` before a candidate is surfaced — rotation-gate
alone, with no corroborating channel, has no defence against this. The score
was not suppressed or altered after this was discovered; it is reported
as-measured, with this explanation attached, in both this file and
`13009518_1920_1080_30fps_physics_result.json`.

The other 8 clips (Accidents-category: `4/7/8/9/11/12/13/14`) have **not**
been reviewed to this same depth and should be treated as open items, not
confirmed positives, until someone checks them the way this one was checked.

**Do not present this as "8/8 validated."** Present it as: the merged
pipeline runs end-to-end on fresh footage and produces a real, inspectable,
non-fabricated score with a full evidence trail — which is itself the
demonstrable claim — while the *correctness* of these particular 8 scores is
an open item for manual review before the demo, not an established result.
`4_physics.mp4`, `7_physics.mp4`, `9_physics.mp4`, and `12_physics.mp4` all
score noticeably lower (0.25–0.31, roughly half the others) than
`11/13/14`'s 0.55–0.60 range — the most plausible "no real event, low
ambiguous score" cases among the eight, and the safer ones to show as
clean-tracking examples rather than confirmed positives.

## Reproduce

```bash
cd FINAL/CCTV
python scripts/render_physics_demo.py --video <path.mp4> --out demo/<name>_physics.mp4
```
